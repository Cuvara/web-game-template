# GameVui — platform contract

What a game built from this template can rely on when it targets GameVui, what it cannot,
and how each is checked. Evidence for every row is in [source-matrix.md](source-matrix.md).

## The one-line version

GameVui publishes **no SDK, no JavaScript API and no publishing API**. The documented way in
is an email to the operator, or its contact form. So there is no GameVui adapter:

```
Game
 ↓
Platform-neutral web build        (@wgf/platform-sdk, generic-web adapter, no portal script)
 ↓
GameVui submission package        (examples/gamevui-compliance-demo → release/gamevui/)
 ↓
Email / contact form to the operator — by a person
```

There is no portal SDK to write an adapter against, so `gamevui` builds use
`GameVuiPlatform` (`packages/platform-sdk/src/adapters/gamevui.ts`), a no-SDK adapter: local
saves, pause on a hidden tab, and every ad `unsupported`. It loads nothing from GameVui.
`pnpm build:platforms` builds it like any other platform into
`build/platforms/gamevui/dist/`.

## What is not here, and why

Nothing in this repository calls, stubs, shims or feature-detects any GameVui global. In
particular there is no `GameVuiSDK.init()`, `GameVui.ads()` or `GameVui.publish()` — none
of them exist in any documentation.

GameVui-hosted games do run GameVui code (source-matrix.md, "SDK — observed,
undocumented" and "Platform script behaviour"):

- a **central** script, `gamevui.vn/games/services/score.min.js`, defines `window.GV`
  (`saveScore`) and `window.GVAdBreak` (a rewarded ad break through Google H5 Games Ads), and
  also injects ads, a menu and a viewport override into the game frame;
- a **per-game** `gamevui-tool.js`, found next to one LayaAir build, defines
  `window.GameVuiTool` with a LayaAir-specific method.

Neither is an API a submitter can target:

- nothing publishes their behaviour, arguments, return values, stability, or whether a
  third-party game may call them at all;
- they are loaded by GameVui around a build it already hosts — the per-game one reads as
  something GameVui writes after receiving a build, not something a build brings;
- code written against them could only be tested on GameVui's production host, and would
  break without notice.

The demo does not call them. It is, however, tested against the behaviour the central
script is observed to impose on a game (viewport override, arrow/space keys swallowed), in
case GameVui adds it to a submission — see GV-TEC-06 in the requirements.

If GameVui ever documents it, the adapter goes in `packages/platform-sdk/src/adapters/` and
this contract changes. Until then, calling it would be inventing an API.

recommended in `compliance/gamevui-compliance-report.md` for the Factory to make, with
`profile_update: requirement-change`.

## When to revisit

- GameVui publishes a developer page, SDK or API → write the adapter against it, replace
  every `UNKNOWN` it settles, and re-run the reviewer.
- The operator answers a submission email with requirements → record the reply's facts in
  source-matrix.md as `OFFICIAL (private correspondence, <date>)`.
- A submission is rejected → the reason goes into the Factory profile's
  `common_rejections`, per docs/publishing.md.
