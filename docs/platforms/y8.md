# Y8

How a game built from this template runs on [Y8](https://www.y8.com/), what the adapter was
checked against, and what is still unverified.

Code: `packages/platform-sdk/src/adapters/y8/` (`platform.ts`, `sdk.ts`, `storage.ts`,
`config.ts`). Profile: `y8@1.0.0` — a Factory core profile, `status: unverified` (see
[Profile](#profile)).

shape. The docs remain the source of truth; the script was used only for two facts the docs
leave open, both marked in code:

- `showAd()`'s promise resolves when the break is queued, not when it ends, and
  `adBreakDone` never fires if Google's ad script is blocked — hence the adapter's watchdogs.
- The code the docs call `Y8Sdk.saveRejected` has the value `"save_rejected"`; `Y8Sdk` is
  not reachable as a global, so the value is written down (`Y8_SAVE_REJECTED`).

## SDK loading

The build puts the documented tag in `<head>` (only for a Y8 build that has an App ID):

```html
<script src="https://cdn.y8.com/minimal-sdk/2-0/y8.min.js" async></script>
```

It is `async`, so it may run before or after the game's module code — the race the docs call
"the most common reason for an SDK that does nothing". `loadY8Sdk()` (`sdk.ts`) follows the
documented cure, in this order:

1. add the `y8sdk.ready` listener;
2. if `window.y8` already exists (the script won the race and its announcement was missed),
   call `y8.emitReadyEvent()` so it announces again;
3. otherwise wait for the tag already in the page, or inject one if there is none.

Only the first `y8sdk.ready` counts (the event can arrive twice: the script's own and the
one requested), and the listener is removed once settled. A blocked script rejects at once;
one that never becomes ready rejects after 10 s. Either way the game boots without Y8.

## Initialization and configuration

The App ID and Game ID come from the game's **SDK Initialization** tab in the
[Y8 Developer Portal](https://developer.y8.com/). They reach the build either on the `y8`
platform entry (`app_id`, `game_id` in `game.config.yaml`) or from the environment, which
wins over the file — the release job's route, which keeps them out of the repository:

```bash
WGF_Y8_APP_ID=<app id> WGF_Y8_GAME_ID=<game id> pnpm build:platforms
```

`src/core/game-config.ts` validates both and fails a `y8` build with no App ID.
`src/main.ts` passes them through `platformOptions(targetPlatform())` to
`createTargetPlatform`, which constructs `Y8Platform` with `{ namespace, config: { appId, gameId } }`;
only a build that targets `y8` carries them.

| Situation                                                 | Build                                                               | Runtime (`platform.mode`)                                          |
| --------------------------------------------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------ |
| App ID and Game ID                                        | `<script async>` in `<head>`                                        | `sdk` — ads and cloud saves                                        |
| App ID only                                               | script in `<head>`                                                  | `sdk` — `init` without `adConfig`; ads report `disabled`           |
| No App ID                                                 | **build fails**                                                     | —                                                                  |
| No App ID, `WGF_ALLOW_UNCONFIGURED_PORTAL=1` (tests only) | warning; no script; `portal_configured: false` (release refuses it) | `not-configured` — SDK never loaded; console error; plain web game |
| Malformed App ID / Game ID in env                         | **build fails**                                                     | —                                                                  |
| Malformed value reaching runtime                          | —                                                                   | App ID: `not-configured`; Game ID: ads `disabled`, console error   |
| Script blocked / never ready                              | —                                                                   | `unavailable` — local saves, ads `not-ready`                       |
| `init()` throws or rejects                                | —                                                                   | `failed` — local saves, ads `not-ready`                            |

The docs give no format for either ID, so validation only requires an identifier
(`[A-Za-z0-9][A-Za-z0-9._-]{0,127}`) and so rejects the docs' own `<app id>` placeholder.

`init` is called once with `{ appId, autoLogin: true }` and, with a Game ID,
`{ gameId, preloadAdBreaks: "on", sound: "on" }` — the documented defaults. `onAuth` is
registered first. `initialize()` then waits (bounded: 3 s, 1.5 s) for the first auth report,
so storage has settled on cloud or local before the game reads its save, and for
`getPlatformLocale()`, which becomes `platform.language` — except `en`, which the docs say is
also the "could not tell" answer, so it is reported as `null` and the game's own fallback
(English) applies.

## Capabilities

| Contract capability            | Y8                     | Why                                                                                           |
| ------------------------------ | ---------------------- | --------------------------------------------------------------------------------------------- |
| `ads`                          | interstitial, rewarded | `next` and `reward` placements. No banner is documented.                                      |
| `cloudSaves`                   | true                   | Cloud Storage — for signed-in players; guests save locally                                    |
| `auth`                         | optional               | "Let guests play"                                                                             |
| `analytics`                    | platform-provided      | plays are counted on init                                                                     |
| `loadingApi`                   | none                   | the SDK has no loading or game-ready call; progress is only counted                           |
| `interstitialMinIntervalS`     | null                   | the SDK paces interstitials itself with a **per-game** interval and reports `frequencyCapped` |
| `gameplayStopOnHidden`         | true                   | Y8 has no gameplay API and no focus handling; the game pauses itself                          |
| `leaderboards`, `achievements` | false                  | Y8 has them; the Platform contract has no call for them yet                                   |
| `iap`                          | false                  | not offered                                                                                   |
| `settings`, `environment`      | defaults               | Y8 imposes no settings and reports no device                                                  |

**Not implemented, because the contract has no place for them:** leaderboards,
achievements, `trackCustomEvent`, `login()`/`logout()` (a game that wants a sign-in button
needs a contract call, which is a cross-platform change), `openProfile`, `isBlacklisted`,
images. None is claimed.

## Ad lifecycle

`showInterstitial()` → `showAd({ type: "next" })`; `showRewarded()` → `showAd({ type: "reward" })`.
`preroll` is never requested ("Requesting it from the SDK is not supported").

```text
request ── beforeAd ─────────────── afterAd ── adBreakDone ──▶ resolve
   │         foreground:lost              foreground:gained
   │         ad:start, hooks.onStart      ad:end
   │
   └─ adBreakDone (noAdPreloaded / frequencyCapped / …) with no beforeAd ──▶ resolve unshown
                        the game is never paused and never muted
```

- **Pause in the callback, not before the call.** A break may show nothing; then Y8 fires
  neither `beforeAd` nor `afterAd`. The adapter raises `ad:start` (which `bindPlatform` turns
  into pause + mute) only on `beforeAd`, and `ad:end` on `afterAd`, so a skipped or capped
  break leaves the game running.
- **`breakStatus` → result.** `viewed`, `dismissed` → `{ shown: true }`. `frequencyCapped` →
  `too-soon`; `noAdPreloaded`, `notReady`, `timeout`, `ignored` → `not-ready`; `error`,
  `other` → `error`.
- **Rewards.** `beforeReward(showAdFn)` calls `showAdFn()` at once — `showRewarded()` _is_ the
  player's choice. `rewarded` is true only when `adViewed` fired (or `breakStatus` is
  `viewed`) — never on `adDismissed`, never for a break that showed nothing. The first of
  `adViewed`/`adDismissed` decides.
- **Exactly once.** Each request resolves once; duplicate callbacks are ignored; `ad:start`
  and `ad:end` are paired.
- **One break at a time.** A second request while one is open (or while a late ad is still on
  screen) resolves `busy`.
- **Timeouts** (all configurable in `Y8Options`):
  - nothing (`beforeAd` or `adBreakDone`) within 15 s → resolved unshown (`error`). This is the
    blocked-AdSense case, where the SDK itself never answers.
  - `beforeAd` but no `afterAd`/`adBreakDone` within 180 s → closed (`shown: true`, no reward)
    so the game is never left paused with no resume callback.
  - `afterAd` but no `adBreakDone` within 2 s → settled on what was seen.
- **Late callbacks.** If an interstitial opens after its request was given up on, it gets its
  own `ad:start`/`ad:end` so the game mutes for it. A rewarded offer (`beforeReward`) that
  arrives after the request was given up on is **declined** — `showAdFn` is not called, so
  nothing plays over a game that has moved on. A rewarded ad accepted in time that opens late
  and is watched through raises `ad:late-reward` once. If a late ad overlaps the next
  request's ad, the foreground is regained only when the last one closes.
- **Hidden tab during an ad.** `bindPlatform` holds the game paused under its own reasons; it
  resumes only when both the ad has ended and the tab is visible.

## Storage

`platform.storage` is `Y8Storage` (`storage.ts`):

| Player    | Backend                                               | `persistent`                  |
| --------- | ----------------------------------------------------- | ----------------------------- |
| signed in | Y8 Cloud Storage (`saveData`/`loadData`/`removeData`) | true                          |
| guest     | local storage, namespaced by game id                  | whatever local storage allows |
| no SDK    | local storage                                         | as above                      |

- Cloud Storage "requires the player to be authenticated", so guests never call it.
- A value over 30 KB (UTF-8) is refused before sending.
- Cloud failures reject with `Y8StorageError`; `.code` carries the SDK code and `.rejected`
  is true for `save_rejected` (refused after the SDK's five retries, up to ~15 s). A failed
  cloud save is never silently written somewhere else — the docs want it visible.
- Signing in or out raises `storage:changed`; re-read anything cached. Guest progress is
  **not** copied to the account automatically: whether a guest save should replace an
  account save is the game's decision, and each key is a request Y8 asks games to spend
  sparingly.
- The docs ask to throttle auto-saves to at most once a minute; that is the game's job.

## Required portal configuration

In the [Y8 Developer Portal](https://developer.y8.com/):

1. Create a studio and a game; open the game's **SDK Initialization** tab.
2. Copy the **App ID** (always) and **Game ID** (for ads) into `WGF_Y8_APP_ID` /
   `WGF_Y8_GAME_ID` in the build environment (a CI secret or variable), or onto the `y8`
   platform entry.
3. To test sign-in from anywhere other than `localhost` (a phone, a tunnel, another machine),
   register that origin on the same tab.
4. Upload the build zip (`pnpm build:platforms && pnpm release:package --release r<n>` →
   `release/r<n>/y8.zip`). While in review, Y8 serves Google's test
   creatives automatically; real ads start once the game is released.

## Local development

- Serve over HTTP (`pnpm dev`, `pnpm preview`); `file://` gives no working SDK.
- A `y8` build without an App ID fails. `WGF_ALLOW_UNCONFIGURED_PORTAL=1 pnpm dev` runs it in
  `not-configured` mode — a plain web game with a console error saying so.
- Off the game's Y8 page nobody is signed in automatically, so storage is local until a
  sign-in; the template has no sign-in call yet.
- Ads: frequency capping is on from the first ad, so a second break in quick succession
  showing nothing is expected — and must leave the game running.

## Profile

The Factory now carries a core profile `y8@1.0.0` (`core/reference/platforms/y8.yaml`,
`status: unverified`); Factory `init` vendors it into a game's `config/platforms/` and
`pinned.json`. The template's own `config/platforms/y8.yaml` is the earlier proposal it grew
from, written only from the docs above; fields the docs are silent on — audience, bundle
limit, review time, metadata — are left out rather than guessed. It is **not** listed in the
template's `pinned.json`.

`y8` is in `KNOWN_PLATFORM_IDS`, so a title can pin `y8@1.0.0`. Release validation evaluates
its one assertion, `y8_sdk_present` (`package.platform_sdk == y8`).

## Known limitations

- **No live ad, reward, auth or storage evidence.** See the table above.
- **No sign-in call in the contract.** Guests stay guests unless the game's Y8 page signs them
  in automatically; a sign-in button needs a Platform contract addition (all portals).
- **No guest → account save migration.** Documented above; the game decides.
- **Leaderboards, achievements, custom analytics events** exist on Y8 and are not reachable
  through the contract.
- **Interval not enforced locally.** Deliberately: the per-game interval lives in Y8's settings;
  a capped break resolves `too-soon` at no cost.
- **Rewarded availability is optimistic.** `adAvailability("rewarded")` is `available` whenever
  the SDK is up with a Game ID; Y8 has no "is an ad ready" query, so a no-fill is only known
  when asked.
- **Browser coverage is Chromium.** Safari's popup rules matter for sign-in (per the docs) but
  sign-in is not exposed yet.
